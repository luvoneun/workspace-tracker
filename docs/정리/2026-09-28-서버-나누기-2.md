## 할 일
1. `routes-items.js`: `GET /api/items`와 그것만 쓰는 목록 읽기 도우미.
2. `routes-track.js`: 항목 추가·수정·삭제·되돌리기 경로(`/api/track/*`, 확인 대기·결정·아이디어·휴지통 등 — `workflowActions`에 있는 것은 제외하고 그대로 둔다).
3. 옮기는 방식은 묶음 1과 같다: 코드 글자 그대로(`return;`→`return true;`, 바뀌는 값은 ctx getter), 모듈은 server.js를 require하지 않는다, 새 파일은 `CLIENT_BLOCKED`에 등록(안 하면 테스트가 실패하는지 확인), `handleRequest`의 분배 순서에 끼운다(복구 가드 뒤, 정적 파일 폴백 앞). `server.js`의 이름·위치·내보내기 유지.
4. 여러 모듈이 같이 쓰는 도우미는 옮기지 말고 ctx로 넘긴다(중복 복사 금지).
- **하지 않는 것**: `readBody().then().catch()` 반복 코드 줄이기, 동작·문구·응답 모양 변경, `workflowActions`·보고서·가져오기 경로, 화면 파일.

## 예외 상황 (반드시 확인)
1. **`readScope`**: 요청마다 새로 만드는 전역 변수라 값을 복사해 넘기면 안 된다 — `ctx`에 **getter**로(요청 순간의 값). 옮긴 목록 읽기 도우미가 같은 캐시를 쓰는지 `GET /api/items`·`GET /api/integrations`의 파일 읽기 횟수 전/후 비교(묶음 1 기준: 7회·11회).
2. **감싸서 다시 대입되는 함수**(`setTrackField = transactional(...)` 등): ctx에는 **감싼 뒤의** 함수가 들어가야 한다(감싸기 전 것을 넘기면 저장 잠금이 빠진다). ctx를 만드는 시점이 감싸기 뒤인지, 또는 getter인지 확인하고, 저장 잠금이 걸리는지 테스트로 확인(기존 테스트가 있으면 그것, 없으면 확인만 하고 보고).
3. **`idempotent`·요청 식별자**: 같은 요청 재시도 처리 그대로.
4. **복구 필요 상태**: 쓰기 경로가 503과 안내 문구로 막히는 것 그대로(가드가 분배기 앞).
5. **오류 응답**: 상태 번호·`error`·`code` 글자 그대로(화면이 글자로 판단).
6. **경로 순서**: `workflowActions`·`/api/report/change`·`/api/import`와 주소가 겹치지 않는지 확인(전부 완전일치).
