# 프로젝트 고정 번호 (명세)

- **왜 만드나**: 직접 만든 프로젝트는 "이름 글자"가 곧 정체성이라, 이름 바꾸기·합치기·지라 에픽으로 옮기기·지우기(그리고 각각의 되돌리기)가 기록 여섯 자리를 저마다 따로 고쳐 쓴다. 새 자리가 하나 생기면 다섯 동작을 다 고쳐야 하고, 하나라도 빠뜨리면 그 자리에서 프로젝트가 조용히 둘로 갈라진다.
- **달라지길 기대하는 사용자 행동**: 없다 — 사람 눈에 보이는 화면·문구·순서는 그대로다. 달라지는 것은 만드는 쪽이다: 프로젝트를 다루는 새 기능(묶음을 직접 만든 프로젝트까지 넓히기, 새 연동)을 넣을 때 "이름이 박힌 자리 여섯 곳"을 다시 찾지 않는다.
- **무엇을 보면 성공인가**: 가짜 데이터의 모든 자리에 이름 `결제 리뉴얼`을 심고 이름 바꾸기·합치기·옮기기·지우기를 한 번씩 한 뒤, 데이터 폴더 전체에서 옛 이름(옛 열쇠)이 **0번** 나온다(주간요약 지우기의 의도된 예외만 빼고). 새 자리를 더하고 표에 안 올리면 그 시험이 빨개진다.

> 결론 먼저: **추천은 C(지금 모양 그대로 + 열쇠 바꾸기 한 곳)** 이다. 번호 표(A)는 교과서적인 답이지만, 이 앱에서는 업무 기록을 사람이 못 읽게 되고, 이름을 글자로 적어 넣는 바깥 작성자(슬랙 수집 스킬·`/track`)가 넷이고, 동료의 옛 앱이 새 데이터를 아예 못 열게 된다. 지라 쪽은 이미 고정 번호(지라 키)가 있어서 문제는 **직접 만든 프로젝트 하나뿐**이다. A로 갈 때(아래 "A로 넘어갈 신호")의 옮기기 계획도 3절에 적어 둔다.
>
> 반대 의견 한 줄: C는 "이름 = 정체성"을 그대로 두므로 이름 바꾸기가 여전히 기록 여러 파일을 다시 쓴다(한 트랜잭션이라 반쯤 바뀌지는 않지만 쓰는 양은 그대로). 직접 만든 프로젝트의 묶음·새 연동이 실제로 정해지면 그때 A의 비용을 다시 따져야 한다.

이름과 지라 번호는 모두 가짜다(`결제 리뉴얼`, `가입 개편`, `PAY-12`).

## 1. 지금 지도 (코드로 확인, 2026-10-08 `d1908db`)

### 1-1. 프로젝트 열쇠는 두 종류

- 지라 프로젝트: `jira:KEY`. 지라 키는 이미 **고정 번호**다. 이름은 지라 요약(앱이 고쳐 쓰지 않음) 또는 앱 안 별칭(`projectAliases`). 이름이 바뀌어도 기록은 그대로이고, 별칭을 바꾸면 주간요약 표시 이름만 다시 짓는다(`setProjectAliasAction` → `reportDrafts.relabelProject`).
- 직접 만든 프로젝트: `group:이름`. **번호도 등록표도 없다.** 항목·회의에 그 이름이 있으면 프로젝트이고(`workflow-store.js` `groupNames`·`groupList`, `server.js` `getCustomGroups`), 하나도 없으면 사라진다.
- 열쇠 짓는 규칙이 세 곳에 같은 꼴로 있다: 화면 `workflows.js:24` `wfKey`, `report-drafts.js:7` `project`, 화면 `app.js:521` `uiProjectColorKey`(색 점). 지라가 걸린 줄은 `group`이 있어도 지라 프로젝트다.
- 파일 표기: 공백 → 밑줄(`group:결제_리뉴얼`), 읽을 때 밑줄 → 공백. 같은 이름 비교는 `groupNameKey`(밑줄→공백·연속 공백 하나·대소문자 무시).

### 1-3. 여섯 자리를 다시 쓰는 동작 — 같은 걷기가 열세 번

| 동작 | server.js | workflow-store.js | report-drafts.js | ⑤ 회의 연결 |
|---|---|---|---|---|
| 이름 바꾸기 | `renameProject` | `renameGroup` | `renameGroup` | 함수 안 반복문 |
| 지라 에픽으로 옮기기 / 되돌리기 | `moveProject` / `undoMoveProject` | `moveGroup` / `undoMoveGroup` | `moveGroup` / `moveGroupUndo` | 각 함수 안 반복문 |
| 합치기·지우기 / 되돌리기 | `mergeProject` / `undoMergeProject` | `mergeGroup` / `undoMergeGroup` | `mergeGroup` / `mergeGroupUndo` | 각 함수 안 반복문 |
| 별칭(지라) | `setProjectAliasAction` | `setProjectAlias` | `relabelProject` | — |

- 모두 `idempotent → mutations.run` 한 트랜잭션(`mutation-store.js` 저널이 실패 시 전부 되돌림)이라 반쯤 바뀌는 일은 없다. 문제는 **안전**이 아니라 **빠뜨림**이다: ① 업무 파일을 줄 단위로 걷는 코드만 다섯 벌(서로 조금씩 다름 — 이름 바꾸기는 id 없는 줄도 바꾸고 합치기는 id 없는 줄이 있으면 거절), ⑤ 회의 연결 반복문 다섯 벌.
- 시험: `server.core.test.js`·`server.jira.test.js`·`server.conflict.test.js`·`client.test.js`에 이 경로들이 있다. 하지만 "모든 자리에서 옛 이름이 사라졌나"를 한 번에 보는 시험은 없다.

### 1-4. 데이터 형식 장치 (A에 필요)

- `migrate.js`: `.data-version`(없으면 1), `DATA_FORMAT_VERSION = 1`, `steps` 비어 있음. 데이터가 앱보다 **새** 형식이면 서버가 시작하지 않는다(server.js 3100). 앱보다 **옛** 형식이면 서버는 막지 않고 옮기지도 않는다 — 옮기기는 `update.sh` 4단계에서만 돈다(2단계가 데이터 백업).
- 옮기기 단계는 `atomicWrite`로만 쓰지만 `mutation-store` 저널 밖이다 — 여러 파일 중 중간에 실패하면 반쯤 옮긴 데이터가 남는다(`update.sh --rollback`으로 백업 데이터를 되돌릴 수는 있다).

## 2. 바꿀 모양 후보

### A. 번호 표 하나 + 기록에는 번호만

- 새 파일 `tracker/.projects.json`: `{ "p_01J…": { "name": "결제 리뉴얼", "jira": "PAY-12" | null, "createdAt" } }`. 지라 프로젝트도 줄을 갖는다(별칭 = `name`).
- 기록 ①~⑥은 `project:p_01J…` 하나만 담는다. `group:`·`jira:` 칸은 항목에서 사라진다(지라 키는 번호 표로 간다).
- **얻는 것**: 이름 바꾸기 = 표 한 줄. 지라 에픽으로 옮기기 = 표의 `jira` 칸 채우기(되돌리기 = 비우기). 묶음을 직접 만든 프로젝트까지 넓힐 수 있음. 새 연동은 표에 칸 하나.
- **잃는 것**: `tracker/*.md`를 사람이 못 읽음(E12). 바깥 작성자 넷(슬랙 수집 스킬 셋·`/track`)이 이름을 적으므로 서버 입구 모든 길에 이름 → 번호 바꾸기가 필요(E11). 이름 비교·같은 이름 막기는 그대로 둬야 함(E2·E9). 합치기·지우기는 여전히 기록을 다시 씀(E4). 항목 칸이 바뀌어 화면·서버의 프로젝트 코드(`group:`·`jira:` 분기 — 앱 파일 19개, grep 기준 450곳 남짓)를 거의 전부 고침.
- **옮기기 비용**: 큼. 형식 번호 2, 여섯 자리 모두 변환, 되돌리는 변환(2 → 1)도 따로 만들어야 옛 앱으로 되돌아갈 수 있음.
- **되돌리기 쉬움**: 어려움. 형식이 올라가면 옛 앱이 시작하지 않는다(E6). 되돌리려면 백업 데이터로 돌아가거나 역변환을 돌려야 함 — 그 사이 쓴 기록은 역변환이 없으면 잃는다.
- **사람이 읽기**: 나쁨.

### B. 기록에는 이름 그대로 + 번호 표는 옆에서 연결만

- 번호 표는 같지만, 기록 ①~⑤는 지금처럼 이름을 담고 **열쇠가 바뀌면 곤란한 옆 표들만** 번호로 묶는다(④ `projectArchive`·③ `projectLinks`·묶음·`weekPolish` 이름 열쇠·`localStorage`).
- **얻는 것**: 사람이 읽기 그대로. 묶음을 직접 만든 프로젝트까지 넓힐 길이 생김. 옛 앱은 기록을 그대로 읽음.
- **잃는 것**: 이름 바꾸기는 여전히 ①②⑤⑥을 다시 쓴다(지금 여섯 → 넷, 대신 번호 표 하나가 더해져 다섯). 기록의 이름과 표의 이름이 어긋나는 **새 실패 모양**이 생긴다 — 옛 앱이 이름을 바꾸면 번호 표는 모른다, 바깥 작성자가 새 이름을 적으면 표에 줄이 없다, 읽기만 하는 요청이 표를 쓸 수는 없다("조회는 파일을 쓰지 않는다").
- **옮기기 비용**: 중간(표 만들기 + 옆 표 열쇠 바꾸기). 형식 번호를 올리지 않을 수 있으나 옛 앱이 만든 어긋남을 고치는 맞추기 규칙이 따로 필요.
- **되돌리기 쉬움**: 중간 — 옛 앱으로 가도 기록은 읽히지만 번호 표와 옆 표는 옛 앱이 모른다.
- **사람이 읽기**: 좋음.
- 판단: 정체성의 출처가 둘(기록의 이름, 표의 번호)이 되어 "두 군데를 맞추는 일"을 하나 더 만든다. 추천하지 않는다.

### C. 지금 모양 그대로 + 열쇠 바꾸기 한 곳 ← 추천

- 데이터 형식·파일·화면은 그대로. 코드만 정리한다:
  1. **자리 표 하나**: `project-keys.js`(새 파일, 서버 쪽)에 1-2절 ①~⑥을 `{ 이름, 읽기, 바꾸기(from, to, mode) → 바뀐 것 기록, 되돌리기(기록) }` 줄로 둔다. ⑦~⑨는 "일부러 안 바꿈"으로 같은 표에 이유와 함께 적는다.
  2. **열쇠 바꾸기 하나**: `rekeyProject({ from: 'group:A', to: 'group:B' | 'jira:KEY' | null, mode })`가 표를 차례로 걷는다. 이름 바꾸기·옮기기·합치기·지우기는 이 함수에 모드만 넘긴다. 되돌리기도 `unrekeyProject(기록)` 하나. 지금의 차이(이름 바꾸기는 id 없는 줄도 바꿈, 합치기는 id 없으면 거절, 지우기는 ⑥을 건드리지 않음, 옮기기는 ③을 지움)는 **모드별 규칙 표**로 옮겨 그대로 지킨다.
  3. **열쇠 짓기 하나**: `wfKey`·`report-drafts.project`·서버 쪽 같은 꼴을 공용 함수 하나로(화면은 `app.js`의 공용 자리, 서버는 `project-keys.js`). 색 점 `uiProjectColorKey`는 지금처럼 열쇠와 다른 값(접두어 없음)을 쓰므로 건드리지 않는다.
  4. **빠뜨림 시험**: 가짜 데이터의 ①~⑥ 모든 자리에 `결제 리뉴얼`을 심고, 동작마다 데이터 폴더 전체를 글자로 훑어 옛 이름이 0번(⑦~⑨·지우기의 ⑥은 표에 적힌 예외만) 남는지 본다. 새 자리를 만들고 표에 안 올리면 이 시험이 실패한다.
- **얻는 것**: "여섯 곳을 다시 찾는" 수고가 표 한 줄로 줄고, 빠뜨림은 시험이 잡는다. 다섯 벌 반복문이 하나로 → 지금 동작 사이의 작은 어긋남이 표에 드러난다. 옮기기·형식 변경·옛 설치 문제 없음.
- **잃는 것**: 이름 바꾸기가 여전히 기록 여러 파일을 다시 쓴다(한 트랜잭션이라 안전, 다만 업무 파일 넷을 통째로 다시 씀). 묶음을 직접 만든 프로젝트로 넓히려면 묶음도 표의 한 자리로 올려야 한다(가능 — 그때 표에 한 줄). 새 연동이 "프로젝트 종류"를 늘리는 위험은 그대로(그때 A를 다시 따짐).
- **옮기기 비용**: 없음. **되돌리기**: 코드 되돌리기만(데이터 그대로). **사람이 읽기**: 그대로.

## 3. 옮기기 계획

### C (추천) — 데이터 옮기기 없음

- 데이터 형식·파일 모양·`.data-version` 그대로. 옛 설치·옛 백업·동료 맥 모두 영향 없음(E6·E7·E10·E15 해당 없음).
- 코드가 바뀌는 동안의 안전: 묶음마다 **바꾸기 전 동작을 고정하는 시험을 먼저** 넣고(지금 코드로 초록), 같은 시험이 바꾼 뒤에도 초록이어야 한다.

### A를 고를 때 — 한 번에, 실패하면 아무것도 안 바뀜

1. **백업 먼저**: `update.sh` 2단계(데이터 백업)가 이미 앞에 있다. 더해서 옮기기 단계 자신이 시작할 때 데이터 폴더 전체를 `.backups/migrate-2-<시각>/`에 복사하고, 복사가 끝나야 다음으로 간다.
2. **한 번에**: 옮기기 단계는 `mutation-store`의 `run()` 안에서 돈다 — 저널이 여섯 자리 모든 파일의 "전"을 남기고, 하나라도 실패하면 저널이 전부 되돌린다. 지금 `migrate.js`는 저널 밖이므로 `steps[2]`를 `mutations.run(() => …)`으로 감싸는 것이 이 묶음의 첫 일이다. `.data-version`은 **저널 안에서 마지막에** 쓴다(데이터가 옛 모양인데 번호만 2인 상태를 막음).
3. **순서**: ① 기록을 모두 읽어 이름 → 번호 표를 짓는다(같은 `groupNameKey` 이름은 한 번호 — 이미 갈라진 둘은 합치지 않고 **둘 다 번호를 따로** 준다, 앱이 합치기를 추측하지 않는다) ② 지라 키마다 줄 하나(별칭이 있으면 `name`) ③ ①~⑥을 번호로 다시 씀 ④ 다시 읽어 "모든 열쇠가 표에 있다"를 확인, 아니면 던져서 저널이 되돌림 ⑤ `.data-version` = 2.
4. **되돌리는 변환**: `steps`에 내려가는 길(2 → 1)이 없다. A를 고르면 `migrate.js --to 1`(번호 → 이름)을 같은 묶음에서 만들고, `update.sh --rollback`이 코드를 옛 버전으로 돌릴 때 데이터를 백업으로 돌리는 대신 이 역변환을 쓸지 정해야 한다(백업으로 돌리면 그 사이 쓴 기록을 잃는다).
5. **옛 앱이 새 데이터를 만나면**: 서버가 시작하지 않고 `이 데이터는 더 새 버전의 앱이 만든 거예요. 앱을 업데이트해 주세요.`(지금 장치 그대로). 동료는 각자 맥이라 섞이지 않지만, 한 사람이 옛 태그로 되돌리면 앱이 안 뜬다.
6. **새 앱이 옛 데이터를 만나면**(E7 옛 백업 복원·E15 만든 사람 설치): 지금 서버는 막지 않는다. A에서는 서버가 시작할 때 `.data-version < DATA_FORMAT_VERSION`이면 옮기기를 직접 돌리거나(백업 → 저널 → 옮기기), 쓰기를 잠그고 "데이터 형식을 바꿔야 해요" 한 줄을 띄워야 한다. 추천은 시작할 때 돌리기(사람이 따로 할 일 없음).
7. **바깥 작성자**(E11): `import-record.js`·`/api/track/*`·회의 담기·`task-batch.js`가 받는 `group` 이름을 서버 입구에서 번호로 바꾼다. 스킬 문서는 그대로 이름을 적게 둔다(사람·AI가 번호를 알 수 없다).
